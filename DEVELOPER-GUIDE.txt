================================================================================
BRIQPAY FOR WOOCOMMERCE - DEVELOPER & INTEGRATOR GUIDE
================================================================================

This guide is intended for developers and technical integrators working with 
the Briqpay for WooCommerce plugin.

--------------------------------------------------------------------------------
1. INSTALLATION
--------------------------------------------------------------------------------
- Standard WordPress Installation: Upload the 'briqpay-for-woocommerce' folder 
  to your '/wp-content/plugins/' directory or upload the ZIP via the admin.
- Activate the plugin through the 'Plugins' menu in WordPress.

--------------------------------------------------------------------------------
2. ENABLING THE GATEWAY
--------------------------------------------------------------------------------
- Once activated, navigate to: WooCommerce > Settings > Payments.
- Locate 'Briqpay' in the list and toggle the switch to 'Enabled'.
- Click 'Finish set up' or 'Manage' to enter the configuration screen.

--------------------------------------------------------------------------------
3. ADMIN CONFIGURATION
--------------------------------------------------------------------------------
- Merchant ID (MID): Your unique identifier provided by Briqpay.
- Shared Secret: Used for API authentication and webhook security.
- Test Mode: Enable this to use the Briqpay Playground/Sandboxed environment.
- Order Management: If enabled, WP will automatically trigger captures/refunds 
  on the Briqpay side when order statuses change in WooCommerce.
- Logging: Enable this during integration to see a detailed trail in 
  WooCommerce > Status > Logs.

--------------------------------------------------------------------------------
4. ORDER MANAGEMENT
--------------------------------------------------------------------------------
The plugin supports both automated and manual order management:

- Automated: 
  - Processing -> Completed: Triggers a full capture.
  - Refund processed in WC: Triggers a refund in Briqpay.
- Manual:
  - Inside the Order Edit screen, a 'Briqpay Payment Details' meta box appears.
  - You can perform partial captures by selecting specific items and quantities.
  - The capture history is displayed directly in the meta box for transparency.
- Auto-capture: If the payment method used for the order has auto-capture
  enabled on Briqpay's side (session data.transactions[].autoCaptureEnabled),
  the 'Manual Capture' button is replaced with an 'Auto capture in progress'
  notice instead, since Briqpay is already handling the capture itself.

--------------------------------------------------------------------------------
5. ACTION SCHEDULER & BACKGROUND PROCESSING
--------------------------------------------------------------------------------
Webhooks from Briqpay are processed asynchronously to ensure high availability
and to prevent timeouts during complex order operations.

- Real-Time Processing: Every session this plugin creates sets
  config.realTimeProcessing to true, so Briqpay delivers webhooks/status
  updates immediately instead of in batches. Note this means event delivery
  order is not guaranteed - the plugin's webhook handling already guards
  against out-of-order delivery (rank-checked status transitions, idempotent
  capture/refund history) for this reason.
- Background Task: Incoming webhooks are enqueued as 'briqpay_v3_process_webhook_callback'.
- Reliability: If a webhook fails to process (e.g., database lock), Action 
  Scheduler will automatically retry.
- Monitoring: You can view the status of these background tasks in:
  WooCommerce > Status > Scheduled Actions.
- Recommendation: For high-volume stores, ensure your server CRON is correctly 
  configured to run the WordPress cron frequently (every minute).

--------------------------------------------------------------------------------
6. RECOMMENDED WOOCOMMERCE SETTINGS
--------------------------------------------------------------------------------
- Guest Checkout: Briqpay works best when 'Allow customers to place orders without 
  an account' is enabled, as it handles the customer identification itself.
- Force SSL: Ensure your checkout page is served over HTTPS; otherwise, 
  the Briqpay iFrame may be blocked by modern browsers.
- HPOS: This plugin is fully compatible with High-Performance Order Storage.
- Terms & Conditions: If a WooCommerce "Terms and conditions" page is configured,
  Checkout_Handler::validate_data_integrity() rejects the purchase unless the
  buyer ticked the native checkbox. The checkbox state is captured in
  ajax_get_session() (the only request that carries the submitted checkout form)
  and stashed in the 'briqpay_terms_accepted' WC session key, because
  ajax_make_decision() only ever posts a sessionId. A never-set flag (e.g. Blocks
  checkout, which submits no classic serialized form) does NOT block.
  Opt out via WooCommerce > Settings > Payments > Briqpay > "Validate Terms &
  Conditions" (setting key 'terms_validation_enabled', read through
  Checkout_Handler::terms_validation_enabled(), which defaults to enabled when
  the key is absent). Turn it off when consent is collected elsewhere - Briqpay's
  own terms module, or a third-party consent plugin - so the buyer is not asked
  twice.

--------------------------------------------------------------------------------
7. THEME & DESIGN INTEGRATION
--------------------------------------------------------------------------------
The Briqpay iFrame is highly dynamic. To ensure it functions correctly:

- Address Fields: When Briqpay is active, it takes control of the address data. 
  If you have custom checkout fields or scripts that manipulate address data, 
  ensure they sync with the WooCommerce Customer object, as the plugin 
  validates the Briqpay session against the WC Cart/Customer state.
- Hiding the Placement Button: The plugin adds a '.briqpay-selected' body class. 
  It uses high-frequency JS sentinels to hide the native 'Place Order' button 
  to avoid conflicting actions.
- Recommendations: 
  - Use standard WooCommerce hooks for UI additions (`woocommerce_before_checkout_form`, etc.).
  - Avoid using CSS `display: none!important` on standard WC checkout containers 
    unless you are targeting the `.briqpay-selected` class specifically.

--------------------------------------------------------------------------------
8. ORDER ATTRIBUTION (Origin column)
--------------------------------------------------------------------------------
WooCommerce's built-in Order Attribution feature (the "Origin" column in
WooCommerce > Orders) only captures data via WC_Checkout::process_checkout(),
which this plugin's storefront checkout never calls - orders are created in
Checkout_Handler::create_order_at_decision(), triggered by our own
'briqpay_make_decision' AJAX action instead. Without help, this shows every
Briqpay order as "Unknown".

- Capture (classic checkout): ajax_get_session() already receives the full
  serialized checkout form as 'checkout_data' on every session sync.
  Checkout_Handler::capture_order_attribution() reads WooCommerce's own
  wc_order_attribution_* hidden fields out of that data (Sourcebuster-derived,
  stamped into the checkout form by WC's own JS) and stashes them in the WC
  session, since the decision AJAX call itself never resends the form.
- Capture (Blocks checkout): Blocks stores this data in the Checkout block's
  own extension data instead of hidden form fields. blocks-checkout.js's
  window.briqpayReadOrderAttribution() reads it client-side - preferring
  WooCommerce's own already-loaded wc_order_attribution.getAttributionData()
  helper, falling back to window.wp.data.select('wc/store/checkout')
  .getExtensionData()['woocommerce/order-attribution'] - and sends it as
  order_attribution in the blocks_data payload. Checkout_Handler::
  capture_order_attribution_from_blocks() stashes it the same way (fields
  arrive already unprefixed, e.g. 'source_type' not
  'wc_order_attribution_source_type').
- Apply: Checkout_Handler::apply_order_attribution_to_order() writes
  whichever path captured data onto the order using WooCommerce's own meta
  key naming (_wc_order_attribution_source_type,
  _wc_order_attribution_utm_source, etc.) once the order is actually created,
  right before it's saved.
- Admin-created orders (Hosted Payment Pages, "Add order" screen) already
  show "Web admin" correctly with no help from this plugin - WooCommerce's
  own OrderAttributionController sets that natively based on is_admin(),
  independent of created_via.

--------------------------------------------------------------------------------
9. HOSTED PAYMENT PAGES
--------------------------------------------------------------------------------
Lets a merchant build an order in the WooCommerce admin and create a
Briqpay-hosted payment link for it, without routing the customer through the
storefront checkout.

- Enable under: WooCommerce > Settings > Payments > Briqpay > Hosted Payment
  Pages. Configure a default flow (pre-selection only), hosted page title,
  logo URL and show-cart preference.
- Flow: POST /v3/session is created first (decision is always disabled -
  nothing calls the decision endpoint for a hosted page, and the WooCommerce
  order already exists), then POST /v3/hosted-page using that sessionId.
- Line item/fee references sent to Briqpay are frozen onto the order's items
  as `_briqpay_item_reference` / `_briqpay_fee_reference` at creation time, so
  a later SKU rename cannot break captures/refunds for that order.
- The order's billing/shipping address and company are prefilled; for the
  Business - Full Checkout flow, whatever Briqpay confirms is written back
  onto the order once the payment webhook arrives.
- Implemented in `includes/class-hosted-payment-page.php`
  (`Briqpay\WooCommerce\Hosted_Payment_Page`).

--------------------------------------------------------------------------------
10. CART SYNC FAILURE FLAG (out-of-sync protection)
--------------------------------------------------------------------------------
Syncing the cart and making the payment decision happen in two different
requests, so a sync failure has to be remembered between them. That is what the
WC session flag Session_Manager::SYNC_FAILED_KEY ('briqpay_sync_failed') is for.
Checkout_Handler::validate_data_integrity() refuses the purchase with "We were
unable to synchronize your cart with the payment provider" while it is set.

Read and write it only through Session_Manager::has_sync_failed() /
::set_sync_failed(), never the raw session key.

Who owns it:
- A successful PATCH in get_or_create_session() clears it.
- create_session() owns it on every other path: a session built from the current
  cart is in sync by construction, so a successful create CLEARS it, and a create
  that errors or returns an unexpected shape SETS it (a stale session id may
  still be cached, and authorizing against that is worse than blocking).
- get_or_create_session() deliberately does NOT set it when a PATCH fails - the
  recovery create_session() immediately after decides. Setting it there would
  survive the successful recovery and refuse the customer's next payment attempt
  even though nothing was out of sync.
- Checkout_Handler::clear_customer_data_after_purchase() and
  Session_Reset_Handler::process_scheduled_session_reset() clear it, so a failure
  from one order or one login context cannot leak into the next checkout.

Debugging a merchant report of that error message: the message is produced by the
decision request, but it is DECIDED by an earlier request. Look further back in
WooCommerce > Status > Logs for 'Direct update failed: <reason>' (debug level) and
'API Error (<code>)' (error level - present even with "Logging" off). A PATCH that
fails while creation succeeds usually means a create-only field (customerType,
modules, country, locale) is reaching the update payload from a merchant filter;
see section 13.

--------------------------------------------------------------------------------
11. WOOCOMMERCE CHECKOUT ACTION PARITY
--------------------------------------------------------------------------------
Storefront orders are created in Checkout_Handler::create_order_at_decision(),
not by WC_Checkout::process_checkout(), so WooCommerce's standard checkout
actions only fire where this plugin fires them by hand. Without them, plugins
that add data at checkout (custom fields, ERP/invoicing connectors, delivery-date
pickers, shipping brokers) silently drop their data on Briqpay orders while
working on every other payment method.

OPT-IN, AND WHY
- Setting: WooCommerce > Settings > Payments > Briqpay > "WooCommerce checkout
  actions" (key 'checkout_hooks_enabled').
- Existing installs are stamped 'no' by Upgrade::maybe_migrate() and opt in
  deliberately; fresh installs default to 'yes'. An existing install is one that
  already has a merchant_id configured.
- Reason it is not simply on: these actions run third-party code during Briqpay
  checkouts where none ran before. In particular, merchants who wrote custom code
  to compensate for the missing actions (typically on briqpay_after_create_order)
  would get both their workaround and the plugins it stood in for - duplicate ERP
  exports, duplicate invoices, duplicate fees.
- register_activation_hook() does NOT fire on plugin updates, which is why the
  migration runs from admin_init keyed on the 'briqpay_wc_version' option.

TWO GROUPS, TWO CALL SITES
The actions split by what they mean, and the split decides where they fire.

  Data hooks - populate the order. Fired in ajax_make_decision() after
  validation has passed and before the decision is sent, which is the last
  moment WooCommerce still has the cart they read from (the return handler
  empties it). Deliberately after validation: this flow creates the order
  BEFORE it validates (the order ID is pushed to Briqpay as reference1), so a
  rejected purchase already has an order row, and firing before validation
  would run plugin code for purchases about to be refused.
    woocommerce_checkout_create_order                ($order, $data)
    woocommerce_checkout_update_order_meta           ($order_id, $data)
    woocommerce_checkout_create_order_line_item_object  (filter, at construction)
    woocommerce_store_api_checkout_update_order_meta ($order)  [Blocks only]

  Commit hooks - signal that a purchase happened. Primary site is
  handle_briqpay_return() beside briqpay_payment_complete: payment is verified
  and the WC session, the posted-data stash and the logged-in user are all still
  present. Webhooks::fire_commit_hooks_fallback() calls the same entry point as
  a FALLBACK for the customer who pays and closes the browser without
  returning; fire_once() means whichever arrives first is the only one that
  runs.
    woocommerce_checkout_order_created               ($order)
    woocommerce_checkout_order_processed             ($order_id, $data, $order)
    woocommerce_store_api_checkout_order_processed   ($order)  [Blocks only]

  Already fired before this feature and NOT gated (they shipped unconditional
  and must stay that way):
    woocommerce_checkout_create_order_line_item
    woocommerce_checkout_create_order_shipping_item
    woocommerce_checkout_create_order_fee_item
    woocommerce_checkout_create_order_coupon_item

THE $data ARGUMENT
Our decision request posts only a sessionId, so there is no submitted form to
pass. ajax_get_session() receives the whole serialized checkout form on every
sync, so it is stashed in the WC session ('briqpay_posted_data') and replayed
when the hooks fire - the same pattern store_order_attribution() already uses for
Order Attribution. Nonces are stripped; the stash is overwritten (never merged)
so a cleared field cannot be replayed as still set; it is cleared by the
post-purchase cleanup and the login reset.

Blocks sends nested address objects, so normalise_blocks_data() maps them to
WooCommerce's flat billing_*/shipping_* keys. Note core WooCommerce Blocks does
NOT fire the classic woocommerce_checkout_update_order_meta - this plugin
deliberately does, because a merchant running Blocks with a classic-hook plugin
is equally broken either way and this plugin is not the Store API.

Many plugins read $_POST directly inside these hooks rather than using $data, so
with_posted_data() superimposes the stash on $_POST and $_REQUEST for the
duration of the do_action() calls only, restoring in a finally. Real request
values win over stashed ones. Disable with the briqpay_superimpose_post_data
filter if it ever causes trouble.

LIMITATION: DATA, NOT AMOUNTS
A plugin can add a fee on woocommerce_checkout_create_order. In core that is safe
because the order is built before payment is authorized. Here the authorized
amount came from the Briqpay session, PATCHed from the cart earlier, so an added
amount makes the WooCommerce total exceed what was authorized and the gap
surfaces at capture. warn_on_total_drift() logs an error naming both amounts when
this happens. It is detection only - silently "correcting" the order would hide a
real configuration problem.

BRIQPAY_PAYMENT_COMPLETE NOW ACTUALLY FIRES
This is the plugin's own action, documented as running when payment is verified at
the return handler. It used to sit only inside the status-upgrade branch of
handle_briqpay_return(). Orders are created as 'pending' at the decision point, so
on a normal storefront purchase that branch is never reached - meaning the action
never fired at all, while the WooCommerce checkout actions beside it did. It now
fires on both return paths, once per order (fire_once group 'verified').

  IF YOU BUILT A WORKAROUND: code you moved to briqpay_after_create_order or a
  webhook hook after discovering this action was dead will now run alongside the
  briqpay_payment_complete listener it replaced. Remove one, or suppress the action
  with the 'briqpay_fire_payment_complete' filter.

Deliberately NOT gated behind the "WooCommerce checkout actions" setting: that gate
exists to stop third-party plugin code running unexpectedly, whereas anything
listening on a Briqpay-specific action is code the merchant wrote themselves.

Also deliberately NOT fired from the webhook. Its meaning is "the customer came
back and we verified the session", not "the money is secured". For the latter use
WooCommerce's own woocommerce_payment_complete, or the order-status transitions -
both already triggered from the webhook via $order->payment_complete(), and both
fire even when the customer never returns. That is the hook an ERP or fulfilment
integration should be on.

OTHER THINGS TO KNOW
- created_via follows the gate: 'checkout' when enabled (a number of plugins gate
  on created_via === 'checkout'), the historical 'Briqpay' when not. Override
  with the briqpay_order_created_via filter. Neither value affects
  Hosted_Payment_Page::is_admin_created_order(), which treats only '' and 'admin'
  as admin-created.
- Hosted Payment Page orders never fire any of these: they are built by an admin
  and have no cart and no checkout form. This is correct, not an oversight.
- Latency: an ERP connector making outbound HTTP calls on
  woocommerce_checkout_order_processed now runs inside the return request, adding
  its round-trip to the customer's wait.
- Idempotency: fire_once() persists '_briqpay_hooks_data' /
  '_briqpay_hooks_commit' order meta BEFORE running the callback, so third-party
  code that fatals cannot earn a second attempt at the same side effects, and a
  customer retrying after a rejected decision does not re-run them.
- Everything is wrapped in catch (\Throwable): these hooks run third-party code
  inside our AJAX handler and the Action Scheduler worker, and an uncaught
  throwable would break the decision response.
- woocommerce_checkout_process (the validation hook) is deliberately NOT fired.
  It belongs in validate_data_integrity() and would hand third-party code a new
  way to block Briqpay checkouts; treat it as a separate decision.
- woocommerce_checkout_create_order_tax_item IS fired, but with a divergence:
  core fires it during construction, before the tax item is added to the order,
  whereas tax lines here come from $order->calculate_totals(true) (core's own
  path) and therefore already exist. fire_tax_item_hooks() offers the action for
  each existing tax line afterwards. A plugin that reads or annotates the item
  works; one that expects to substitute the object does not.

WHAT ELSE WC_CHECKOUT DOES THAT THIS FLOW NOW MATCHES
These are defect fixes, not new third-party behaviour, so they apply regardless
of the setting:
- Line items record the product's tax class. Without it a later recalculation in
  the admin taxes a reduced-rate product at the standard rate.
- Shipping items copy the rate's tax_status and its own metadata
  ($rate->get_meta_data()). Table-rate, pickup-point and broker plugins store the
  customer's chosen service there.
- Coupon items store the 'coupon_info' snapshot, so an order still renders its
  discounts after the coupon is edited or deleted.
- apply_native_order_properties() sets the cart hash and the customer note. The
  note comes from the stashed form: 'order_comments' on classic, 'customer_note'
  on Blocks. An existing note is never overwritten.

Behind the setting, because they change behaviour:
- reserve_stock() calls wc_reserve_stock_for_order() at the decision, so a
  purchase in flight cannot be oversold to the next customer. A reservation
  failure is logged, never thrown - by that point Briqpay is about to authorize
  and refusing would be worse. release_stock() runs on the validation-failed
  branch so a refused purchase does not hold stock until the reservation expires.
- recalculate_cogs() calls calculate_cogs_total_value() on WooCommerce 9.5+.
- woocommerce_checkout_order_exception fires from ajax_make_decision()'s catch,
  wrapped so a listener cannot mask the original error from the customer.

NATIVE CHECKOUT ENTRY POINTS
- Gateway::process_payment() no longer returns failure unconditionally. It
  succeeds ONLY when session_is_paid_for_order() confirms payment by calling the
  Briqpay API - never from local meta, and treating a missing session, an API
  error or an unexpected response shape as unpaid. Anything unconfirmed keeps the
  previous behaviour of blocking, so the native button cannot bypass payment.
- Checkout_Handler::handle_checkout_order_processed() is hooked to
  woocommerce_checkout_order_processed. It existed for a long time but was never
  registered, so orders created by WooCommerce's own pipeline never had their
  Briqpay session attached. It carries three guards, all load-bearing:
    1. If '_briqpay_hooks_commit' is already set we are the source of the action
       (fire_once() stamps before its callback) and there is nothing to do.
    2. Otherwise WooCommerce fired it and every listener has already run, so the
       flag is stamped to stop fire_commit_hooks() firing them again. This is how
       "do not fire manually when native checkout already did" is enforced.
    3. Status is promoted from a draft state only. The original method set
       'pending' unconditionally; with the action now also firing from the webhook
       fallback that would have downgraded an order already at 'processing'.

STILL NOT COVERED
Deliberately out of scope - they need matching release-on-failure logic or a
larger change to how orders are created:
- Coupon usage holds (wc_get_coupon_held_keys and their release).
- Submitting the storefront purchase through WC_Checkout::process_checkout()
  itself, and submitting Blocks through the Store API Checkout route instead of
  hiding the Place Order button. That is the structurally correct end state and
  would make most of this section unnecessary, but it is a rewrite of the
  checkout flow rather than an addition to it.

--------------------------------------------------------------------------------
12. CONCURRENCY, IDEMPOTENCY AND MONEY
--------------------------------------------------------------------------------
ATOMIC LOCKS (Briqpay\WooCommerce\Lock)
The plugin previously guarded critical sections with:

    if (get_transient($key)) { bail; }
    set_transient($key, 1, 30);

That is a check-then-set race: two concurrent requests can both pass the read
before either writes. Consequences were real - two decision requests for one
session creating two WooCommerce orders, one webhook delivery processed twice.

Lock uses add_option(), which is a single INSERT against a uniquely-indexed
column, so exactly one concurrent caller can succeed and the database itself
arbitrates. wp_cache_add() is deliberately NOT used: it is only atomic when a
persistent object cache is installed and degrades silently to per-request memory
when one is not. Locks are stored with autoload off and carry an expiry, so a
request that dies mid-flight cannot wedge a session permanently.

    Lock::acquire($key, $ttl)  - mutual exclusion; release when done
    Lock::release($key)
    Lock::claim_once($key, $ttl) - idempotency marker, never released
    Lock::is_held($key)        - informational only, never branch on it

Where locks are held:
  - ajax_make_decision()                  'briqpay_decision_lock_<session>'
  - Webhooks::handle_webhook()            per-event dedup via claim_once()
  - Order_Management::capture_order()     'briqpay_capture_<order>'
  - Order_Management::refund_order()      'briqpay_refund_<order>'
  - Hosted_Payment_Page::ajax_create...() 'briqpay_hpp_<order>'

Captures, refunds and hosted page creation previously had no lock at all, so two
rapid admin clicks could double-capture, over-refund, or invalidate a hosted page
link already emailed to the customer.

ACTION SCHEDULER ENQUEUE RESULT
as_enqueue_async_action() returns 0 when it could not schedule. That return used
to be ignored, so the webhook was dropped - and because the dedup marker was
already claimed, Briqpay's retry was discarded as a duplicate and the event was
lost entirely. The result is now checked and the payload processed inline instead.

MONEY (Briqpay\WooCommerce\Money)
Briqpay amounts are integers in the currency's minor unit. This plugin has
historically hard-coded that as x100 / /100 at every call site, which is correct
only for two-decimal currencies. A zero-decimal currency (JPY, ISK, KRW) would be
sent 100x too large, a three-decimal one (KWD, BHD) 10x too small.

Money is now the single definition of that conversion:
    Money::to_minor($amount) / Money::from_minor($minor)
    Money::decimals()   - wc_get_price_decimals(), filterable via
                          'briqpay_money_decimals'
    Money::multiplier()
    Money::is_supported_precision() - true only at 2 decimals

Gateway::is_available() returns false when precision is unsupported, so the
gateway hides itself rather than taking payment for the wrong sum. Override with
'briqpay_allow_unsupported_currency_precision' if a setup has been verified.

The remaining x100 call sites throughout the plugin are equivalent to to_minor()
while that guard pins precision at two decimals. Migrating them is follow-up work;
doing it before the guard existed would only have moved the bug around.

AMOUNT-ONLY REFUNDS
A refund entered as an amount rather than per item cannot be attributed to
specific captured lines. It used to divide by 1.25 - a hard-coded 25% Swedish VAT
- and send a fictional 'physical' product called "refund".
derive_order_tax_rate_bps() now takes the rate from the order itself: the order's
tax total over its net (the blended rate the customer actually paid), falling back
to the highest line-item rate, falling back to zero. Never a guess - inventing tax
that was never charged is not recoverable. The line is sent as productType
'adjustment' carrying the refund reason. Allocating across real captured
references is left to the 'briqpay_amount_only_refund_items' filter.

13. DEVELOPER HOOKS (ACTIONS & FILTERS)
--------------------------------------------------------------------------------
Integrators can customize the plugin behavior using the following hooks:

FILTERS:
- `briqpay_create_session_data`: (array) Modify the payload sent to Briqpay when 
  creating a checkout session.
- `briqpay_update_session_data`: (array, string) Modify the update payload.
- `briqpay_cart_items`: (array) Filter the cart items list before it is mapped 
  to the Briqpay format.
- `briqpay_is_available`: (bool) Programmatically enable/disable the gateway.
- `briqpay_order_metadata`: (array) Add custom metadata to the WC Order when
  created via Briqpay.
- `briqpay_hpp_session_data`: (array, order, flow) Modify the /v3/session
  payload used to back a hosted payment page.
- `briqpay_hpp_config`: (array) Modify the /v3/hosted-page config
  (pageTitle, logoUrl, showCart).
- `briqpay_hpp_billing_address` / `briqpay_hpp_shipping_address`: (array, order)
  Modify the address blocks derived from the order for a hosted payment page.
- `briqpay_hpp_locale`: (string) Modify the locale sent for a hosted payment
  page session.
- `briqpay_fire_checkout_hook`: (bool, string) Disable one specific WooCommerce
  checkout action while leaving the others enabled. See section 11.
- `briqpay_superimpose_post_data`: (bool, array) Disable superimposing the
  stashed checkout form on $_POST while the checkout actions fire, passing it
  only as the hook argument. See section 11.
- `briqpay_order_created_via`: (string) Override the created_via value stamped on
  storefront Briqpay orders ('checkout' or 'Briqpay'). See section 11.
- `briqpay_money_decimals`: (int) Decimal precision used for minor-unit
  conversion. See section 12.
- `briqpay_allow_unsupported_currency_precision`: (bool, int) Allow the gateway to
  run on a store whose precision is not 2 decimals. See section 12.
- `briqpay_amount_only_refund_items`: (array, float, order) Replace the single
  adjustment line used for an amount-only refund, e.g. to allocate across the
  actual captured references. See section 12.

ACTIONS:
- `briqpay_before_create_session`: (array) Runs before the API call.
- `briqpay_after_create_session`: (result, array) Runs after session creation.
- `briqpay_webhook_received`: (data, session, order) Triggered when a
  validated webhook event is processed (session/order-status fall-through only).
- `briqpay_webhook_session_verified`: (data, session, order) Triggered for
  EVERY verified webhook, including capture_status/refund_status/order_status.
- `briqpay_fire_payment_complete`: (bool, order) Suppress
  `briqpay_payment_complete`. Only needed if you built a workaround while that
  action was unreachable - see section 11.
- `briqpay_payment_complete`: (order, session) Runs when the payment is
  fully verified at the return handler.
- `briqpay_hpp_before_create` / `briqpay_hpp_created`: (order, flow, ...)
  Run before/after a hosted payment page is created.

14. MIGRATING FROM THE PREVIOUS PLUGIN (LEGACY B2B META MAPPING)
--------------------------------------------------------------------------------
For stores migrating from the previous "Briqpay for WooCommerce" plugin
(github.com/krokedil/briqpay-for-woocommerce, v1 API), B2B orders can
additionally be stored using that plugin's order meta keys, so existing
ERP exports/integrations built against those keys keep working unchanged.

- Setting: WooCommerce > Settings > Payments > Briqpay > Migration / legacy
  compatibility > "Legacy B2B order meta mapping". Off by default.
- Implemented in `includes/class-legacy-b2b-meta.php`
  (`Briqpay\WooCommerce\Legacy_B2b_Meta`), a static utility with no init()
  dependency for its core logic - only its admin-display hooks are
  registered via `Legacy_B2b_Meta::init()`, called from
  `on_plugins_loaded()` alongside the other components.
- This is additive, not a replacement: this plugin's own current meta keys
  (`_briqpay_company_cin`, `_briqpay_company_name`, `_briqpay_psp_name`,
  `_briqpay_auto_capture_enabled`, ...) are always written regardless of the
  setting, because Hosted_Payment_Page and B2b_Checkout's admin box read them.
  When the setting is on, the legacy keys below are written on top.
- B2B detection (`Legacy_B2b_Meta::is_b2b_session()`) is derived purely from
  the Briqpay session payload (top-level or nested `customerType ===
  'business'`, falling back to a non-empty `data.company.cin`/`name`) - it
  cannot use B2b_Checkout::is_b2b_active()'s WC session/cookie logic, because
  the webhook and Hosted Payment Page call sites run with neither available.

Meta key mapping (legacy key -> source):
  _billing_org_nr                       <- data.company.cin
  _shipping_email                       <- data.shipping.email, falls back to
                                            data.billing.email
  (shipping phone, via set_shipping_phone()) <- data.shipping.phoneNumber,
                                            falls back to data.billing.phoneNumber
                                            (guarded with is_callable(), method
                                            is WC 5.6+; skipped on older WC)
  _briqpay_payment_method               <- order's `_briqpay_psp_name` meta,
                                            falls back to
                                            get_payment_method_title()
  _briqpay_autocapture                  <- 1 or '' (legacy stored a raw
                                            truthy/empty value), mirroring
                                            Order_Management::
                                            session_has_auto_capture_enabled()
  _briqpay_rules_result                 <- always '[]'; the underlying
                                            feature was deprecated in the v3
                                            API, kept only for shape parity
  _briqpay_psp_update_order_supported   <- only written when
                                            data.transactions[0].
                                            pspSupportedOrderOperations.
                                            updateOrderSupported === true

Call sites writing legacy meta (`Legacy_B2b_Meta::apply($order, $session)`,
called right before each `$order->save()`):
  - Checkout_Handler::create_order_at_decision() (main storefront path)
  - Checkout_Handler's iframe-return handler
  - Webhooks (no WC session available - relies on payload-only B2B detection)
  - Hosted_Payment_Page::maybe_sync_from_session() (Business - Full Checkout)

Read-side fallback (ungated, works regardless of the setting):
  - `Legacy_B2b_Meta::get_company_cin($order)` reads `_briqpay_company_cin`,
    falling back to `_billing_org_nr`. Used by Hosted_Payment_Page::
    get_company() and B2b_Checkout::display_company_in_admin(), so an order
    imported from the old plugin (which only ever set `_billing_org_nr`)
    still resolves correctly.
  - When the setting is on, B2b_Checkout::display_company_in_admin() is a
    no-op - Legacy_B2b_Meta renders its own "Billing Organization Number"
    field on the order screen instead, matching the previous plugin's UI,
    to avoid showing the CIN twice.

Explicitly out of scope: `_capture_id_` (the old plugin's capture-completed
marker; this plugin uses `_briqpay_captures`/`_briqpay_capture_history`
instead) is not mirrored, since only the stored B2B fields feed the
customer's ERP, not the capture bookkeeping keys.

CODE EXAMPLE: MANIPULATING THE SESSION PAYLOAD
--------------------------------------------------------------------------------
Add this to your theme's functions.php or a custom plugin:

add_filter('briqpay_create_session_data', 'my_custom_briqpay_payload');
function my_custom_briqpay_payload($data) {
    // Add custom metadata to the Briqpay session
    $data['metadata'] = array(
        'source_platform' => 'Custom Integrator v1.0',
        'referral_code'   => 'SALE2024'
    );
    
    // Force a specific locale if needed
    $data['locale'] = 'sv-se';
    
    return $data;
}
